# Подготовка выпуска

Версия задаётся в `VERSION`. Workflow Release запускается вручную, принимает
существующий тег вида `v1.3.0` и по умолчанию создаёт черновик предварительного
выпуска. Он не создаёт тег и не изменяет ветки.

1. Проверьте выбранный коммит: CI трёх ОС, испытания готового пакета и ограничения.
   Обновите VERSION, CHANGELOG и инструкции пакетов.
2. Создайте и отправьте тег на проверенном коммите:

   ```sh
   git tag -a v1.3.0 -m "Zaslon 1.3.0"
   git push origin v1.3.0
   ```

3. В Actions → Release → Run workflow выберите тег `v1.3.0` в
   `Use workflow from` и оставьте `publish: false`.
   Тег должен совпадать с VERSION. Сборки используют проверенный SHA коммита;
   перенос тега во время сборки запрещает публикацию.
   Запуск с ветки отклоняется: тег контекста GitHub должен совпадать с исходниками
   и сведениями о происхождении артефактов. Через CLI:

   ```sh
   gh workflow run release.yml --ref v1.3.0 -F publish=false
   ```
4. Проверьте черновик: пять архивов (Windows/Linux AMD64/ARM64, macOS universal),
   контрольные суммы, `install.ps1`, `install.sh`, общий `SHA256SUMS.txt` и заметки выпуска.
5. После приёмки опубликуйте черновик как предварительный выпуск.
   `publish: true` нужен только для сознательной публикации сразу после сборки.
   Существующий выпуск workflow не перезаписывает.

CI выполняет нативные тесты, сборку и проверку пакетов на трёх ОС, а также
офлайн-тесты установщика и передачу работающей защиты на Windows.
Происхождение архивов, установщика и общего списка сумм записывается через
GitHub artifact attestations. Самообновление остаётся отключённым.
Linux/macOS дополнительно проходят `scripts/Test-UnixInstaller.sh` с частным
HOME/XDG и без запуска защиты. Проверяются обновление, ярлыки, сохранность
конфига/журнала, безопасное удаление и macOS-подпись после копирования.
Нативный macOS-прогон выполняется на Intel; сборка universal также содержит
Apple Silicon. Нативное выполнение установщика на ARM64 этим не подтверждается.

Установщик получает версию при сборке через `go run ./tools/release`.
Шаблоны требуют явного `-Version` (PowerShell) либо `--version` (sh).

Черновики доступны через авторизованный GitHub CLI. Пример Linux AMD64:

```sh
gh release download v1.3.0 --repo avazar/zaslon --dir zaslon-test --pattern install.sh --pattern SHA256SUMS.txt --pattern 'zaslon-1.3.0-linux-*.tar.gz'
cd zaslon-test
sh install.sh --package ./zaslon-1.3.0-linux-amd64.tar.gz --checksums ./SHA256SUMS.txt --no-start
~/.local/bin/zaslon
```

Для ARM64 выберите соответствующий архив. Офлайн-удаление выполняется тем же
скриптом и пакетом, с добавленным `--uninstall` после выхода из приложения.
Явный режим установки helper не запускает защиту. Обычные режимы восстановления
сохраняют независимость от сети и config.yaml.

Офлайн-проверка Windows после сборки пакетов:

```powershell
.\scripts\Test-Installer.ps1 -WindowsPackage .\dist\zaslon-1.3.0-windows-amd64.zip
```

Тест использует свои папки, не запускает защиту и не меняет ярлыки или автозапуск.
Сквозной сценарий `tools/domain-e2e` принимает `-installer-package <полный путь ZIP>`.
Запускайте GUI-EXE через `Start-Process -WindowStyle Hidden -Wait -PassThru`
и проверяйте ExitCode. Все потомки ограничены Windows Job Object; срок прогона
с установщиком — 150 секунд. Отчёты остаются в игнорируемом `build/audit/`.
Сценарий также проверяет возврат предыдущих файлов и перезапуск при искусственном
сбое запуска новой версии, без продвижения heartbeat приостановленных процессов.

Для офлайн-развёртывания есть `-PackagePath` и `-ChecksumPath` из одного
доверенного выпуска. `-NoStart` допустим только для неработающего экземпляра.
`-InstallDirectory` выбирает постоянную папку. Для изолированного профиля нужны
`-ProfileDirectory` и `-NoShortcut`; запускайте с тем же ZASLON_DIR.
Перед удалением выйдите из трея. Настройки и `Zaslon.backup-*` сохраняются.
Ошибочные `Zaslon.stage-*` и `Zaslon.failed-*` могут остаться для диагностики;
не удаляйте бэкапы до проверки установленной версии.
